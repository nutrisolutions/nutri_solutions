### Fixed — Sent chat messages appeared twice until a page refresh
- The server emits `message:new` to every conversation member's socket room, including the sender's own — so a sent message was appended once from the REST response and a second time from the sender's own socket echo. Refreshing loaded the true (single) stored message, making the duplicate look like a refresh-only bug. Fixed by routing both append paths (REST response + socket event) through one `appendMessage` helper that dedupes on `message._id` (`client/src/pages/chat/ChatPage.jsx`).

### Added — Internal company chat (Phase 1: 1:1 DMs + HR/admin-managed groups)
- **Real-time transport**: added `socket.io` (server) / `socket.io-client` (client). `server/src/realtime/socket.js` — a single Socket.io server with a JWT-verifying connection middleware that accepts *either* an Admin or an Employee token (any department/status, unlike the HR-only admin-panel bridge below), joining each socket to a personal `user:<kind>:<id>` room. `server/src/middleware/chatAuth.js` (`requireChatAuth`, `resolveChatIdentity`) does the same identity resolution for the REST side.
- **Data model**: `server/src/models/Conversation.js` (`type: "dm"|"group"`, `members[]`, `createdBy`, `lastMessageAt`/`lastMessagePreview` for inbox sorting) and `server/src/models/Message.js` (sender, body, per-member `readBy[]` receipts).
- **Chat API** (`server/src/services/chatService.js`, `controllers/chatController.js`, `routes/chatRoutes.js`, mounted at `/api/chat`): company-wide directory (`GET /directory` — every Employee + Admin, self excluded), find-or-create DM, list-my-conversations (with unread counts), get/post messages, mark-read. Sending a message persists it and emits `message:new` to every member's room.
- **Groups** (`server/src/controllers/chatGroupAdminController.js`, routes under `/api/admin/chat/groups`): create/rename/add-remove-members/delete gated `requireRole("superadmin","hr")` (so HR-department employees riding the admin-panel bridge get this too) — the creator is always auto-included as a member. **Superadmin-only oversight**: `GET /api/admin/chat/groups` (every group in the company) and `GET /api/admin/chat/groups/:id/messages` (read any group's full history without needing membership) — deliberately does not extend to DMs, which stay private between their two participants.
- **Frontend**: `client/src/context/ChatContext.jsx` picks whichever session (admin or employee) is currently logged in, connects the socket, and tracks conversations + a total unread count exposed as a nav badge. `client/src/pages/chat/ChatPage.jsx` (shared page, rendered at both `/admin/chat` and `/portal/chat`) — conversation list, thread view, "New chat" directory search, "New group" creation (HR/admin only). Added "Chat" nav entries with unread badges to both `AdminLayout.jsx` and `PortalLayout.jsx`.
- Verified end-to-end against the running dev server: minted real tokens, confirmed the directory correctly excludes self, DM creation, message send/receive over REST, and — critically — a live `socket.io-client` connection receiving `message:new` in real time the instant another user posted a message.
- Not yet built (flagged as phase 2, not part of this pass): audio calls (planned to reuse the existing Jitsi integration rather than build custom WebRTC signaling) and a live call-busy status.

### Added — HR-department employees get Recruitment & People / Workforce access from inside the employee portal
- Admin and Employee are two fully separate login/token systems (`Admin` model + JWT `role` vs `Employee` model + JWT `role: "employee"`, enforced by separate `requireAuth`/`requireEmployeeAuth` route guards and separate React layouts/contexts) — there was no prior linkage between an employee's department and any admin-side permission.
- `server/src/middleware/auth.js`'s `requireAuth` now also accepts an employee JWT **if** that employee's department is named "Human Resources" and they aren't suspended (looked up per-request), mapping them to `req.admin = { role: "hr", isHrEmployee: true, ... }` — so every existing `requireRole("superadmin","hr",...)` check on admin routes just works for them, no route-level changes needed. Added `requireCoreAdmin` to explicitly block these HR-employee tokens from Content (Projects/Blogs/Tech Stack) and Insights (Analytics/Contact) — sections outside what was asked for — applied across the relevant routes in `server/src/routes/adminRoutes.js`.
- `client/src/context/EmployeeAuthContext.jsx` mirrors the employee's token onto the admin-facing `api` axios instance on login/bootstrap/logout (so the *existing* admin page components' API calls, built on that instance, carry a valid token) and exposes `isHr` (`employee.department.name === "Human Resources"`).

- **Self-action restrictions** (added after finding an HR employee could otherwise assign tasks to themselves or open their own record): `createTask` (`server/src/controllers/taskAdminController.js`) 403s "You cannot assign a task to yourself" when `req.admin.isHrEmployee` and the target equals the requester; `getEmployee` (`employeeAdminController.js`) 403s "You cannot view or manage your own employee record here" likewise. Client-side: the Tasks "Assign to" dropdown shows the HR employee's own name as a disabled option labeled "(you — cannot self-assign)" (initially hidden entirely, but that emptied the dropdown for companies with few employees, so switched to disabled-with-label per follow-up); the Employees list marks their own row "(You)" and clicking it shows the restriction message instead of opening the detail view.

### Added — Offer rejection (with reason), auto-expiry, suspension, and regeneration
- Employee can now **reject** an offer (`client/src/pages/portal/PortalOfferPage.jsx`), required to type a reason first (inline form, mirrors the existing leave-request-reject-reason pattern). `POST /api/employees/me/offer/reject` (new, `employeePortalController.js`) stores `offerRejectedAt`/`offerRejectionReason` on `Employee` and notifies HR with the reason included.
- **Auto-expiry**: if an employee's offer is still `offer_sent` and today is past their `joiningDate`, `server/src/utils/offerExpiry.js`'s `expireOfferIfNeeded()` (checked lazily on login/`getMe`/`getOffer` — no cron needed) flips them to a new `offer_expired` status and cuts portal access (`employeeLogin`/`getMe` 403 with an explanatory message, which the existing `EmployeeAuthContext` failure-handling already logs out on).
- Rejection itself does **not** block login/portal access — only expiry (automatic) and **suspension** (an explicit new HR action, `PUT /api/admin/employees/:id/suspend`, `setSuspended` in `employeeAdminController.js`) do. This was a deliberate correction after an early pass over-applied the access-cut to rejection too; the working model is: reject = record + let HR decide, suspend = HR's explicit lever to cut access, expire = automatic cut.
- HR can **regenerate** the offer after a rejection or expiry: `generateOffer` now accepts `offer_rejected`/`offer_expired` (previously only `documents_verified`), and `AdminEmployeesPage.jsx`'s Offer section shows the rejection reason / expiry note plus a "Regenerate offer" button in that state.
- New `Employee` model fields: `offerRejectedAt`, `offerRejectionReason`, `suspended`, `suspendedAt`; new statuses `offer_rejected`/`offer_expired` (plus `"system"` added to `statusHistory.changedBy` enum for the auto-expiry's audit entry). `client/src/lib/employeeStatus.js` got matching labels/badges. Admin employee detail header gained a Suspend/Unsuspend button + "Suspended" badge.

### Added — Preview-before-send for all HR-generated documents (offer, joining letter, payslip, appraisal)
- Previously, generating any of these documents immediately made it visible to the employee (and, for offer letters, immediately advanced their status). Now generation is a two-step **stage → preview → send** flow: HR clicks Generate, the PDF(s) open automatically in a new tab for review, and nothing is visible to the employee until HR explicitly clicks Send.
- **Offer/joining letters**: `generateOffer` now writes to new `offerLetterDraftUrl`/`joiningLetterDraftUrl` fields instead of the real (employee-visible) ones, and no longer touches `status` or notifies anyone. A new `POST /api/admin/employees/:id/offer/send` (`sendOffer`) copies the drafts into the real `offerLetterUrl`/`joiningLetterUrl`, flips status to `offer_sent`, and notifies the employee — this is the only path that does so now.
- **Payslips/appraisal letters**: `server/src/models/CompanyDocument.js` gained a `sent` flag (default `false`) and a `metadata` field (used to defer the appraisal's CTC bump until send time, rather than applying it at generation). Generating opens the PDF in a new tab and creates the doc as an unsent draft (no notification). New `PUT /api/admin/employees/:employeeId/company-documents/:docId/send` (`sendCompanyDocument`) flips `sent`, applies any deferred metadata, and notifies. The employee-facing `listMyCompanyDocuments` now filters to `sent: true`, so drafts are invisible to them; the admin-facing list shows a Draft/Sent badge with a per-document "Send to employee" button.

### Changed — Payslip generation: Auto vs Manual amount mode

### Changed — Auth tokens moved from localStorage to sessionStorage (per-tab sessions)
- `client/src/context/AuthContext.jsx` and `EmployeeAuthContext.jsx` now store the JWT in `sessionStorage` instead of `localStorage`. `localStorage` is shared across every tab of the same origin, so logging into a second account in a new tab silently logged out the first tab; `sessionStorage` is tab-isolated by default, so different tabs can now hold different logged-in accounts (a browser "duplicate tab" action still copies `sessionStorage`, so a duplicated tab starts out sharing the session until it logs in as someone else).

### Fixed — Employee creation broke after the first employee without an `employeeCode`
- Found while testing the Jitsi change below: `Employee.employeeCode` was `{ default: null, unique: true, sparse: true }`. A sparse unique index only skips documents where the field is *missing*, not documents where it's explicitly `null` — so every employee without a code got `employeeCode: null` written, and the second such employee hit an `E11000 duplicate key` on creation (surfaced to HR as a generic "Employee already exists" 409). Removed the `default: null` (`server/src/models/Employee.js`) so the field is genuinely absent until `generateOffer` sets a real code, and backfilled the dev DB (`$unset` on the 3 affected documents) so existing data satisfies the sparse index too.

### Fixed — Leave requests failed with "No leave balance found for this leave type"
- `convertToPermanent` only sets `employee.leaveBalances` from whatever `LeaveType`s exist *at conversion time*. Employees converted before any leave types existed (i.e. before the default-seed fix above) ended up with an empty `leaveBalances` map, so `createLeaveRequest` in `server/src/controllers/employeePortalController.js` hard-failed with a 400 instead of falling back to the leave type's default allowance. Made the balance lookup self-healing: if an employee has no stored balance for a given leave type, it now looks up that `LeaveType`'s `defaultDaysPerYear`, persists it onto the employee, and continues — instead of erroring. Also backfilled `leaveBalances` for the two existing permanent employees in the dev DB so this doesn't need to self-heal on their first request.

### Changed — Payslips and appraisal letters are now server-generated, not HR-uploaded files

### Fixed — Excessive blank space per page + added a digital signature block
